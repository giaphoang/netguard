# Architecture experiments in AI Agent

Send an objective to **AI Agent** on the live native Linux dashboard. Preparing a performance experiment collects live evidence and sends benchmark traffic within the isolated fabric. Open **Tool activity** in the reply to inspect the calls, inputs, outputs, and timestamps. Review the prediction, selected endpoints, configuration diff, and rollback before choosing **Approve change and benchmark**. The controller checks the live topology and configuration again before applying the preview.

Use **Experiments** in the chat header to reopen saved runs. The reply includes a permalink and a link to the complete evidence. Older architecture workspace links resolve to the saved run in AI Agent.

The dashboard process requires root on the Linux host running the local Docker daemon. The Ubuntu guest needs `iperf3` and the tools from the guest setup instructions. Run `sudo apt install --no-install-recommends iperf3` on the guest if needed. The benchmark processes run inside the lab endpoint network namespaces and use the guest's CPU budget. The UI links to a JSON record with the model, prompt version, topology, command arguments and outcomes, prediction, approval, verification, and rollback. [Ubuntu setup](UTM_ARM64_SETUP.md) · [iperf3 options](https://software.es.net/iperf/invoking.html)

Configuration changes last for the lifetime of the managed containers. **Restore original configuration** reverts the recorded changes and checks connectivity. The controller reserves the fabric during an experiment and while its configuration is deployed, so incident injection and topology deployment wait until restoration. Packet loss, path loss, failed benchmarks, or an emergency stop during implementation trigger rollback. A pending preview expires after 15 minutes.

## Double aggregate throughput

The lab checks BGP and route coverage, runs a single-flow diagnostic, and measures three four-second TCP trials with eight parallel flows. It also samples ICMP under load, reads VM CPU counters, and measures the distribution of transmit bytes on the source leaf's spine interfaces. When the two-address workload concentrates on one path under Linux Layer 3 hashing, the lab can propose Layer 4 hashing on the endpoint leaves. A third spine and increased VM capacity are evaluated against observed path use and shared VM resources. [Linux multipath hash policies](https://docs.kernel.org/networking/ip-sysctl.html#ip-variables)

In the saved Ubuntu ARM64 run, TCP goodput was 155.76 Gbps at baseline and 127.42 Gbps after the change. The 2× target was 311.51 Gbps. The change shifted transmit traffic from nearly all on one spine to 51.6% and 48.4% across both spines. Two paths were installed in both directions and all 75 ICMP samples in each arm returned. Median guest CPU utilization exceeded 95% in both arms, and the per-trial throughput ranges overlapped. Physical link capacity, the cause of the variance, and long-term availability require separate measurements. [Experiment 1b7d7929](proof/architecture/throughput.json) · [Chrome result](proof/architecture/throughput.png)

## GRE overlay

Ask the Agent to design and benchmark GRE or name two current access leaves. The lab verifies the routed underlay, inspects the MTU of eligible ECMP egress interfaces, checks local kernel support, and measures the direct path. The GRE plan uses a dedicated IPv4 /30 and subtracts 24 bytes for the outer IPv4 header and basic GRE header. The React Flow preview draws the overlay as a dashed connection between the selected leaves. The design review compares GRE, IPv4-in-IPv4, and MPLS using the guest's module inventory and the forwarding configuration each option needs. [GRE standard](https://datatracker.ietf.org/doc/html/rfc2784) · [IPv4-in-IPv4 standard](https://www.rfc-editor.org/rfc/rfc2003.html) · [Linux MPLS controls](https://docs.kernel.org/networking/mpls-sysctl.html)

After approval, the lab verifies the tunnel devices and their routes, sends do-not-fragment pings at and above the predicted MTU, and captures the outbound and inbound GRE packets with `tcpdump`. The direct and tunneled arms use the same router namespaces and workload with their respective underlay and overlay addresses. BGP and ordinary host reachability are verified independently. The GRE option is benchmarked by this workflow. IP-in-IP and MPLS require their own measurements.

In the saved run, the direct path carried 1,500-byte IPv4 packets and 139.78 Gbps median TCP goodput. GRE carried 1,476-byte IPv4 packets, matching the prediction, and delivered 126.85 Gbps against a 137.48 Gbps estimate. The p95 ICMP RTT was 0.122 ms direct and 0.113 ms through GRE, with zero sampled loss and two installed underlay paths in both arms. The trial ranges overlapped. Chrome exercised approval and restoration, and an emergency-stop run automatically deleted the two experiment-owned interfaces and verified the restored underlay. ## Paired diagnosis workflow evaluation

Ask the Agent to compare the current diagnosis workflow with a candidate prompt and retrieval strategy on the same recorded incidents. The comparison alternates workflow order by case and runs each profile against the same labeled observation with the same local model. The candidate supplies abnormal and missing link evidence, coverage counts, and host probe results. Both profiles use the live assessment guard. The suite records input hashes, model digest, per-case decisions, errors, tool usage, incorrect repair suggestions, and required human handoffs. Results appear in the chat reply and AI Impact.

The saved Qwen run used 11 cases per workflow, with recorded observations and labeled variants covering four- and six-router fabrics, a dual link failure, and ambiguous evidence. The current workflow diagnosed 6/11 cases correctly and the candidate diagnosed 7/11. Both workflows made 7/7 required handoffs with zero incorrect repair suggestions in this run. The candidate halved average context size from 884 to 451 bytes. Median per-case latency was 0.94 s versus 0.92 s, while mean latency was 0.89 s versus 1.01 s. The candidate missed both BGP-only cases and two ambiguous cases. The recorded recommendation is to advance the candidate to a held-out evaluation before considering promotion. [Experiment 9822751a](proof/architecture/workflow-evaluation.json) · [Chrome result](proof/architecture/workflow-evaluation.png)

## Compare routing convergence

Ask for an isolated trial of two or more of BGP, OSPF, and IS-IS. **Awaiting approval** appears after the installed FRR parser and Compose validate the files. Review the topology, fault scope, saved predictions, and configurations in the reply before choosing **Approve and run comparison**. The native Ubuntu guest needs local Docker Compose 2.36 or later for deterministic interface names. [Compose interface naming](https://docs.docker.com/reference/compose-file/services/#interface_name)

Each protocol gets a fresh two-spine, two-leaf network with two test hosts. Spine 1 carries baseline traffic and Spine 2 is the standby. The controller checks both leaves’ primary routes, the adjacencies, and bidirectional connectivity before disabling the trial Leaf 1 interface facing Spine 1. It samples the two leaves’ kernel routes and sends 100 numbered ICMP probes at roughly 100 ms intervals. The result uses the first sample of the final stable period and reports missing replies during the probe window. FRR neighbor snapshots show the control-plane transition and the full run records the raw outputs. Each trial is removed before the next one starts, and the controller verifies the active fabric after cleanup.

The saved result covers one run per protocol on the Ubuntu VM. Probe spacing, route sampling, and guest scheduling bound timing precision. Results apply to this topology, configured timers, and fault type. [Approved browser run and measured evidence](proof/architecture/routing-approval.json)
